# MovieLens 1M 五维评分 v2 研究提案

状态：v2 已采用。用户确认低于 20 部不同电影的用户不因该指标被清洗删除；具体实现以代码和 `iteration1-design.md` 为准。

## 依据与数据特点

- [GroupLens 的 MovieLens 1M README](https://files.grouplens.org/datasets/movielens/ml-1m-README.txt)规定三表结构、1–5 整数评分、Unix 秒时间戳、UserID 1–6040、MovieID 1–3952；人口属性由用户自愿填写，未核验真实性，电影资料可能有手工录入错误。
- [Harper 与 Konstan 的数据集论文](https://files.grouplens.org/papers/harper-tiis2015.pdf)给出 ML-1M 的评分时间为 2000 年 4 月至 2003 年 2 月，矩阵密度约 4.47%；2001–2002 年评分较少是数据抽样的特点。矩阵中未观察到的用户－电影组合不应算作“缺失字段”。
- [ISO/IEC 25012 的公开简介](https://www.iso.org/obp/ui/?_escaped_fragment_=iso%3Astd%3Aiso-iec%3A25012%3Aed-1%3Av1%3Aen)把数据质量放在具体使用情境中定义。[ISO/IEC 25024 的公开摘要](https://committee.iso.org/standard/35749.html?browse=ics)允许按情境设计量化指标，并未给出通用的合格分数阈值。下列公式是本项目的设计，不是 ISO 指定公式。

### 当前实现暴露的问题

在当前工作区的三份 `.dat` 文件上，直接运行 `govern.py` 的默认清洗与评估逻辑（按文件顺序读取；不是一次 Hadoop 作业）得到：原始 1,161,652 行，清洗保留 1,008,766 行，移除 152,886 行（13.16%）。清洗后 Accurate、Complete、Unique、Consistent 均为 100%，而 Up-to-date 从 1.97% 变为 2.27%。这些数字针对本地含异常的副本，不能当作官方 MovieLens 1M 的质量结论。

1. 清洗规则和评分判定高度重合；删除违规行即可让前四项变为 100%，分数没有说明损失了多少可用数据。
2. 四维把三表所有行放在同一个分母，ratings.dat 占本地总行数约 99.02%，用户表与电影表的质量几乎被淹没。
3. `score_freshness=365` 把固定历史快照当成持续更新的数据源，给正常的早期评分扣分；是否“对今天的新电影及时”无法由该快照证明。
4. 当前时间上限是 2003-02-01 00:00 UTC。论文只给出“至 2003 年 2 月”的月份范围；本地有 1,496 条其他主要字段有效、时间落在 2003 年 2 月的评分会被这个上限排除。它们是否属于官方原版仍需来源核验。
5. 现在的一致性没有检查同一 `(UserID, MovieID, Timestamp)` 对应不同 Rating 的冲突；当前去重会按确定性排序保留一条，但排序不能证明哪条真实。

## 推荐口径：五维质量分 + 评估覆盖 + 有效留存

评分规则固定为独立的 `quality-spec-v2`，不随清洗规则开关改变。每次评估保存评分规范版本、数据版本、时间窗口和各维分子／分母。清洗前后只比较同一规范与同一原始数据源下的结果。

对维度 `d`、适用表 `t`：

```text
质量分 Q[d,t] = 100 × 本维合格且可评估的行数 / 本维可评估行数
评估覆盖 A[d,t] = 100 × 本维可评估行数 / 该表实际行数
有效留存 Y[d,t] = 100 × 清洗后本维合格行数 / 清洗前该表实际行数
```

可评估行数为零时 `Q` 显示 N/A，不显示 100。清洗前后的 `Q` 展示交付数据质量；`A` 告诉用户有多少行无法判断；`Y` 使用固定的原始分母，防止仅靠大量删除获得漂亮的分数。`Y` 是保留下来的有效数据比例，不把删除异常记录误称为“修复”。三表适用的维度以三表等权平均作为总览分，同时必须展示每表结果、分子和分母；时间维度只适用于 ratings.dat。不另造一个五维加权总分。

| 维度 | 可评估对象与合格条件 | 不计入本维的内容 |
| --- | --- | --- |
| Complete 完整性 | 每张表的**所有物理行**均可评估；须能按 `::` 解析出规定字段数，且所有必填字段非空白；用户还须有至少 20 部不同电影的可信评分。 | 未观察到的用户－电影评分组合；无法从文件证明从未收集的用户或电影。 |
| Accurate 可验证正确性 | 结构完整的行；检查规范整数、正 ID、MovieLens 1M 官方 ID 范围、性别／年龄／职业编码、1–5 整数评分与 18 种电影类型。 | 真实人口属性、片名事实、ZIP 地理真实性；这些缺乏外部真值。Timestamp 的值域交给时间维度。UI 应标明“规则有效性”，避免声称现实准确率。 |
| Unique 唯一性 | 能解析业务键的行；users 用 UserID，movies 用 MovieID，ratings 用 `(UserID, MovieID, Timestamp)`。按键分组，`不同键数 / 可评估行数`，同时报告完全重复行、同键不同内容的数量。 | 同一用户－电影在不同时间的再次评分先列为诊断信息；没有足够依据直接判为重复。 |
| Up-to-date 历史时间适配性 | 能解析四字段的 ratings 行；Timestamp 须为规范 Unix **秒**，且位于有出处的历史采集月份。暂定 `[2000-04-01, 2003-03-01)` UTC，边界可配置并记版本。 | 对当下推荐业务的实时新鲜度；固定归档无法给出这项分数。`T1/T2` 仅为时间切分边界，不参与质量分。 |
| Consistent 一致性 | 具有可解析 ID 的记录；同一 UserID／MovieID 的属性无冲突、评分引用唯一且有效的用户和电影、同一评分事件无不同 Rating。冲突按完整键组判定，不依赖文件顺序。 | 用户偏好是否合理、电影上映年份和评分日期的事实关系；无外部证据时只提示，不自动扣分。 |

每项记录可评估数、不合格数、不可评估数及具体子规则计数。`Complete` 覆盖率天然为 100%，但其质量分包含无法解析的行；其他维度的不可评估行留在覆盖率中，不应悄悄消失。可选清洗规则（例如 ZIP 模式、电影片名年份）可以另作诊断，但不自动改变固定评分口径。

## 对比与报告

- 五维卡片：每项显示清洗前 `Q`、清洗后 `Q`、百分点变化、清洗后 `A/Y`；可展开 users/movies/ratings 的分子分母和子检查失败数。
- 卡片旁单列处置账本：各表原始、保留、规范化、去重、隔离数量；保留用户数、电影数、评分数及每用户评分数分布。官方 README 的“每用户至少 20 条评分”是数据集选择特征；清洗后低于 20 应提示下游建模风险，不据此删除用户。
- 如果质量分上升而有效留存下降，报告同时说明两者；不得把隔离异常描述成修复。若某维评估覆盖偏低，醒目标明该分数依据不足。
- 报告记录时间窗口依据、评分规范版本和来源文件版本。不同规范版本的分数不直接比较。

## 实现时需要的步骤

1. 在 Hadoop 评分作业中分别统计三表、五维及子检查的 `good/eligible/unassessable`；对唯一性和冲突用分组聚合，避免“第一条为准”的顺序依赖。
2. 将评估规则定义与清洗规则目录分开，并固定 `quality-spec-v2`；保存窗口配置和规则版本。调整 2003 年 2 月的时间边界前，先核对官方文件及当前 HDFS 源文件来源。
3. 让对比工具读取同一原始基线，计算固定分母的有效留存；更新前端五维卡片、评分规则弹窗和 Markdown 报告。旧任务保留 v1 算法版本，不重解释其历史分数。
4. 用官方原版和本地异常副本各做一轮回归，并注入“删除大量有效行”“同键不同评分”“毫秒时间戳”“2003 年 2 月评分”等样例验证口径。

## 其他可选方案

- **只换时间维度、保留四维现状**：改动最小，但 100 分与删除比例的问题仍在。
- **五维各折算成一个惩罚删除的综合分**：界面紧凑，但权重难解释，同一删除会牵连所有维度，也容易掩盖“数据洁净但留存低”。不建议作为默认。
- **严格把 Up-to-date 标为 N/A，另增时间有效性维度**：语义最准确，但与本项目要求输出五维数字的格式不一致；可在报告说明中保留此解释。
